  What this fix does

  Completes the half-done previous attempt. do_match was left with a try: block
  at line 134 that had no matching except/finally — the file wouldn't even
  parse, so Render's last deploy would have crashed at import. The fix:

  1. Re-indents the rest of do_match (token gen, profile fetch, set_user_room,
  set_partner, call_history insert, notifications, timer creation) into the
  existing try: block.
  2. Adds except asyncio.CancelledError that pushes the popped partner back onto
   waiting_queue if the match task is cancelled after find_match returned but
  before set_partner ran — this is the exact race that strands users in stale
  state.
  3. Re-raises so the outer disconnect-handling finally in websocket_match still
   runs.

  Already in place (from the prior commit 47bf31b, no further changes needed)

  - WebSocket finally block — pops active_connections, calls _full_room_cleanup,
   removes from queue
  - cancel handler — remove_from_queue + call_ended manual + close
  - end_call handler — _full_room_cleanup writes call_history (ended_at,
  duration_seconds, ended_by), deletes both users' rooms, notifies partner,
  cancels timer
  - clear_stale_state on startup — wipes waiting_queue, user_room:*, partner:*
  - TTLs — ROOM_TTL=2100s (35 min) on user_room + partner keys; safety margin
  over CALL_DURATION=1800s
  - Atomic queue ops — add_to_queue uses Redis pipeline (LREM + LPUSH);
  find_match uses blocking BRPOP

  One note on your requirements

  You asked for set_user_room TTL = 60s, but CALL_DURATION = 1800s (30 min). A
  60s TTL would expire mid-call and break disconnect detection. Current 2100s
  correctly auto-cleans 5 min after the longest possible call. If you actually
  want shorter, lower CALL_DURATION first.

  Real problem (architecture bug — mera kal wala fix sirf SyntaxError ka tha)

  Tumhare app me ek fundamental race condition hai jo matching ko silently kill
  kar raha hai. Ye sequence dekho:

  T+0s   Phone 1 → /matching → WS open → queue = [P1]
  T+0s   Phone 1 ka do_match brpop pop karta hai → khud hi pop hua (self)
         → re-queue → "waiting" send → TASK KHATAM ho gaya
         (Phone 1 ab queue me hai but uska matcher dead hai!)

  T+5s   Phone 2 → /matching → WS open → queue = [P2, P1]
  T+5s   Phone 2 ka do_match brpop pop karta hai → P1 milta hai → MATCH!
  T+5s   Backend dono ko "matched" event bhejta hai ✅

  T+5s+ε Phone 1 Flutter: matched event mila → context.go('/call')
         → MatchingScreen.dispose() → WS close
  T+5s+ε Phone 2 Flutter: same

  T+5s+ε Backend Phone 1 WS handler: receive_text() throws disconnect
         → finally block chala
         → get_user_room(P1) returns channel_name (abhi-abhi set hua)
         → _full_room_cleanup CHAL JATA HAI 💀
         → Partner ko "partner_left" bhejta hai
         → Redis state delete

  T+5s+ε Phone 2 /call screen mein pohcha lekin uska partner already "chala
  gaya" mark ho gaya
         → call_ended event mila → wapas /home

  hai. Architecture ka bug hai — /matching se /call pe navigate karne ka
